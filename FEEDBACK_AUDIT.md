# Pressto — Engineering Feedback Audit

Eleven items raised by the team, checked one by one against the real backend
and admin-panel code — not against what the screens are supposed to do. Each
entry says what exists today, what's actually missing or broken, and the
concrete change required.

**Scope audited:** `pressto_backend` + `pressto-admin-panel`
**Method:** direct code audit, no assumptions

## Summary

| Real gaps to build | Confirmed bugs | Needs a decision | Already shipped |
|---|---|---|---|
| 7 | 2 | 1 | 1 |

---

## 1. Split & multi-drop delivery, with a remark — Dispatch screen

**Status:** Gap

**Where it stands:** Split-with-remark exists, but only on the Order Status
screen (`order-status-split-dialog.js`) — one remark field, no address.
`Order.deliveryAddress` is a single scalar column, so a split can't carry
different drop addresses. Both Dispatch screens only offer one-address-at-a-time
changes, with no remark at all.

**What's required:** Give a split (or a dispatch-method change) a per-drop
address, and turn its remark into an append-only log — same pattern as
`OrderStatusHistory` already used everywhere else — instead of overwriting one
field. Then surface it on the Dispatch screens themselves.

- Scope: Backend + Admin Panel
- Files: `order.service.ts`, dispatch views
- Effort: Large

---

## 2. Same capability — permission module

**Status:** Gap

**Where it stands:** `dispatch:*` and `delivery:*` permissions exist, but
splitting an order is gated by the generic `order:create` permission. There's
no permission slug for "split" a role can be given on its own.

**What's required:** Add a dedicated slug (e.g. `order:split`), gate the
endpoint and new UI on it, and add it to the permission seed so it can be
handed to, say, a store manager without full order-creation rights.

- Scope: Backend permissions
- Bundle with item 1
- Effort: Small

---

## 3. Order Summary — complete, end to end

**Status:** Gap

**Where it stands:** Totals, payments, items and status history are all real
API data. But the garment "Current Position / Working Process / Transfer"
columns are fabricated — the screen literally shows a `"Tracking: Demo Data"`
chip, generated by cycling `index % 3`, with no backend call behind it.

**What's required:** Swap the generator for real calls — this session already
built what it needs: garment `currentStoreId`/`currentStoreName` and
`GET /garments/{id}/process-status`. No new backend work, just wiring and
removing the demo chip.

- Scope: Admin Panel only
- Files: `order-summary-view.js`
- Effort: Medium

---

## 4. Address popup — pincode as the only mandatory field

**Status:** Gap

**Where it stands:** Today's form also requires Flat/House name, Building
name, City and State — pincode is just one of several. The backend
`CustomerAddress` model is stricter still: it requires `addressLine1`/`city`/
`state` too, so even a relaxed form would be rejected by the API.

**What's required:** Relax both layers to pincode-only. Keep what already
exists as the safety net: 6-digit format validation, and city/state auto-fill
from pincode — an address stays verifiable with fewer required fields, not
less verified.

- Scope: Backend + Admin Panel
- Files: `customer-address.model.ts`
- Effort: Small–Medium

---

## 5. Finance — change a payment's method after the fact

**Status:** Gap

**Where it stands:** A payment can be created and read, never edited — no
endpoint touches `paymentMode` after the fact, and no admin control exists
either. A `finance` role already exists in the permission seed, but no
`payment:update`-style permission exists for it to hold.

**What's required:** A correction endpoint (e.g.
`PATCH /orders/{id}/payments/{paymentId}`), a new permission granted to
`finance`, and a small edit control wherever payment history is already
listed in the admin panel.

- Scope: Backend + Admin Panel + permissions
- Files: `PaymentTransaction`
- Effort: Medium

---

## 6. POS Inspection — the remarks field already there is silently dropped

**Status:** Bug

**Where it stands:** An "Additional Note" field already exists on the
inspection screen and looks like it works — character counter, shows on the
challan preview. It just never reaches the backend: the function that builds
the save payload only reads the preset instructions dropdown, never this
field.

**What's required:** A one-function fix — merge the note into the same
`instructions` payload the preset dropdown already uses. The backend field it
should land in already exists and already works for the dropdown.

- Scope: Admin Panel only
- Files: `order-item-extras-catalog.js`
- Effort: Small

---

## 7. "Order placed by" filter

**Status:** Needs a decision

**Where it stands:** The Order Status list already has a "Placed by" column —
but it's the customer's household contact who dropped items off, not the
staff member who created the order. There's no field anywhere tracking which
staff user created an order, and no filter for either meaning today.

**What's required:** Confirm which one is meant. Household contact: just add
a filter, the data's already there. Staff attribution (more likely what's
wanted): needs a new field captured at order creation, then the filter.

- Scope: Admin Panel, or + Backend
- Pending: which "placed by"
- Effort: Small (existing data) or Medium (new field)

---

## 8. Finance — move money out of a customer's wallet

**Status:** Gap

**Where it stands:** `WalletService.debit()` already exists and works — but
nothing in the codebase calls it. Every wallet endpoint is credit-only
(recharge, refund-to-wallet). The "Debit" label in the admin wallet panel is a
ledger filter, not a button.

**What's required:** Expose the existing method through a new endpoint with a
required reason, gated to finance, plus the matching action button in the
wallet panel. The hard part — the debit logic itself — is already built and
just needs a door.

- Scope: Backend (small) + Admin Panel
- Files: `wallet.service.ts`
- Effort: Small

---

## 9. Sales return — refunding short by the GST amount

**Status:** Bug — priority regardless of size (real money)

**Where it stands:** GST is applied once, at the order level, on top of a
pre-tax subtotal — `OrderItem.totalPrice` is itself pre-tax. Sales-return
reads that same pre-tax figure as the refund amount and subtracts it straight
from the GST-inclusive order total, for both the credit note and the wallet
refund. Every return pays the customer back less than they actually paid, by
the GST portion.

**What's required:** Compute each returned item's proportional share of the
order's GST and refund the tax-inclusive figure, in the preview calculation
and the actual credit/wallet-refund path alike. Real money-correctness fix —
needs careful testing against real orders before it ships.

- Scope: Backend
- Files: `sales-return.controller.ts`
- Effort: Medium

---

## 10. Return the whole order — multi-select, shared or individual reasons

**Status:** Already done

**Where it stands:** Already fully built: per-item checkboxes, a "select all"
control with an indeterminate state, one shared reason by default, and an
"individual reason per item" override that swaps in a reason field for each
item. The backend already accepts an array of items in a single call. The
dialog's own copy already says exactly this: *"Select multiple items or the
entire order. All selected items are returned together in one credit note."*

- Nothing to build
- Worth confirming the team has actually tried this screen

---

## 11. Rejected-at-intake indicator on Manage Order

**Status:** Gap

**Where it stands:** Done at the item level — Order Details already shows a
proper "Rejected at Intake" chip, and disables the relevant actions. But the
Manage Order *list* screen — the one the team actually means — has no
reference to it at all, so there's no way to spot a rejected item without
opening every order.

**What's required:** Add a cheap per-order flag to the list response (an
aggregate, not a full item join) and a small badge on the row when it's true
— the same visual treatment as the existing "Edit Order" row-action icon.

- Scope: Backend (small) + Admin Panel
- Files: `order-status-view.js` list query
- Effort: Small–Medium

---

## Sequencing note

Items 6 and 8 are the cheapest wins — a wiring fix and exposing code that
already exists in both cases. Item 9 is the one that touches real money and
deserves priority regardless of size.
